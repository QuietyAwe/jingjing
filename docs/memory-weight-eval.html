用例设计

模拟一段真实陪伴：每天早中晚各打招呼、闲聊、道别，中间穿插真正提起往事。记忆按被提起的方式分五组：
  • hot「巷口面馆」每天提一次 —— 检验常提的事能不能一直保持清晰
  • lowfreq「周末去西山」每 3 天提一次 —— 低频提起的边界
  • stopped 提过 1~2 次后就不再提 —— 应该自然淡忘，不该永生
  • never 从未被提起的 6 条 —— 一旦被误报强化并长期占位，就是「误报被长期提醒」
  • ritual「早安问候」「睡前晚安」—— 每天打招呼/道别会命中，单列观察
每轮先跑检索，再按策略强化，最后按真实衰减曲线逐小时采样。判定口径：权重 ≥60 = 细节清晰、占记忆区前排；≥40 = 还在记忆区；<40 = 冷记忆不再主动冒头。「误提醒小时」= 从未被真正提起的记忆处于 ≥60 的总小时数。

结论

1. 两个目标可以同时满足，但主力不是「改复习给多少」，而是「管住谁能触发复习」。 C 档（新检索 + 保留你原本的「一次复习清零」）：常提的面馆清晰 132h / 末权重 75，保持得住；从未被提过的记忆误提醒从 95h 降到 0h；不相干误报轮 7 → 0；真提召回仍 100%。 2. 现状（A）的危害不只是「这一轮冒三条」。7 天里闲聊有 7 轮撞上不相干记忆：两条从未被提过的事被顶到清晰档共 95h；「妈妈做的番茄炒蛋」只真提过 2 次，却被误报顶得清晰 129h；「周末去西山」被误报 4 轮，窗口末权重还有 90。停提组清晰 171h，理想基线只有 84h —— 多出来的全是误报复习。这也是最初只看「末权重」会漏判的地方。 3. 「攒几次才到位」（我上一轮的推荐）被这份用例证伪，不该单独用。 - B（旧检索 + 累进 35）确实把长期误提醒压到 0h，但本轮误报仍有 7 轮，用户体感没改善； - B2 把增量调大到 +60，天天被撞的误报又攒回 35h，说明调参数挡不住重复误报； - D（新检索 + 累进 35）最糟：从冷记忆起步要爬 3 天，常提清晰小时 132h → 37h、末权重掉到 57，反而把常提的事拖模糊了。 保留「被真正想起一次就立刻清晰」+ 干净的准入门槛，比累进更贴合人类回想，也不需要新增参数。 4. 残留边界：C 档里「晚安」「早上好」每天命中同名记忆，仪式组累计清晰 191h。若认定这也算误报，加会话时机闸门（E 档）可归零到 0h，常提保持不变；代价是要把会话状态（距上轮时长 / 是否首条末条）传进检索层，无法从内容判断。这是唯一需要外部信号的一档。 5. 口径说明：早版「停提后淡忘」只看窗口末权重，会漏掉「被误报长期顶着、最后刚好掉下来」的情况，故补了停提组清晰小时与理想基线对照。

评估边界

  • 检索用真实 tokenize.ts + 停用词表 + 屏蔽词判定；SQL 粗召回用等价字符串包含模拟。衰减按 decay.ts 的 daily/priority 5 公式复刻（项目无 node_modules，别名模块无法直接 import）。
  • 未纳入 episode 类型（按天衰减、下限 15）、权重优先级 1~9 差异、灵光一闪概率通道、Prompt 拼装细节。
  • 「会话闸门」（E 档）用轮次角色模拟运行时信号（距上轮时长 / 是否首条末条），不是从内容判意图。真实接入需把会话状态传进检索层。

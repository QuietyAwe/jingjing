评估边界

  • 分词（tokenize.ts）、屏蔽词（isBlockedGram）、门槛与打分（minHitScore / rankByOverlap）均取自真实源码并实际执行；SQL 粗召回用等价的字符串包含模拟。
  • 不含权重衰减、灵光一闪概率通道、Prompt 拼装；未模拟别名表与真实多片段库（每条事件用 2 条片段拼接），真实库的片段更多，召回可能略高于本评估。
  • 理想命中按「真实陪伴场景下什么算恰当」人工标注，情绪类用例带有语义期待，纯字符串检索天然难以满足——这正是评估要暴露的。
  • 复跑：node --experimental-strip-types tests/retrieval.eval.mjs，会重新生成本报告。

结论

1. 当前改动（V1）是净负收益。Precision 64.9% → 75.0%，但 Recall 80.0% → 40.0%，逐例完全正确 68.2% → 54.5%。副作用误触发 8 → 4 例确有改善，代价是 44 条里多错 6 条。 2. 回归集中在最核心的场景：换说法 6/6 → 2/6、时间词 3/3 → 1/3、身份名 2/3 → 0/3、多主题长句 2/3 → 1/3；改善只落在寒暄 5/9 → 6/9、闲聊 4/5 → 5/5、边界 2/4 → 3/4。也就是「不翻旧账」变好了，「想起往事」明显变差——后者才是陪伴 App 的主功能。 3. 根因：minHitScore 把门槛绑在「输入关键词总数」上。bigram 枚举让长句必然带一堆噪音 bigram，而一条真正相关的记忆往往只共享 1 个实词；长输入被要求 ≥2 分，「我母亲最近身体还好吗」「阿柚今天又加班了」「上周感冒好点没」全被挡掉。相对截断又进一步丢掉多主题长句里的次相关事件。 4. 单纯放宽回不去：V2/V3 把 Recall 恢复到 76.7%、完全正确回到 68.2%，但副作用误触发回升到 7 例。「早上好 / 早安 / 晚安」是真实词且库里有同名记忆，属于触发时机问题，与打分门槛无关。 5. 建议换判据，而不是继续调数值：① 命中只认关键字段（event_text / alias / keywords），summary / gist 的模板话不算实质命中——等于复用写入时 LLM 已做过的语义判断；② 单词问候交给会话开场信号；③ 单字「猫」被分词层丢弃，单独处理。三者都不需要词表。 6. 固有短板：情绪倾诉 D 组改动前后都是 1/5，纯字符串检索无法从「今天好累」联想到「加班到很晚」，属架构限制，不是本次改动引入。

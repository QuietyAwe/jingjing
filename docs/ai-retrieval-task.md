# AI 检索判定改造任务书

> 状态：已实施（未发布）· 均为 JS/TS 改动，可走 OTA 发布 · AGENTS.md 与 PRD 的检索相关章节已同步

## 一、目标

把「这句话想起了哪些往事」的判定从本地关键词规则交给 AI：

- 消除漏报：50% 截断误丢、无字面重合的语义联想（累→加班、overtime→加班、拉铁→拿铁）；
- 消除误注入：否定句、硬干扰、近邻混淆不再靠字面混进记忆区；
- 擦亮只在真想起时发生；
- **详略跟档位与指认的细节走**：明确在谈的事只把被指到的那条细节给完整段落、其余留一行印象，只是提到相关人事物的连细节都不展开；
- **能证明唤不起往事的轮次不调 AI**（覆盖检查），**已经被遗忘的不再参与判定**（权重 <15 不进清单），其余轮次照判；
- 判定过程落库沉淀，成为可复盘、可反哺标注集的数据资产；
- 成本靠前缀缓存压到每轮几厘钱。

依据：78 例离线核对——误命中 29/29 可由 AI 判掉；漏报 11 处中 3 处靠放宽候选可捞回，8 处字面无重合、只有全量清单能让 AI 联想。

## 二、架构总览

| 层 | 职责 |
| --- | --- |
| 本地 | 覆盖检查（整句是否只有寒暄/语法成分）＋ 遗忘过滤（权重 <15 不进清单）＋ 兜底检索 ＋ 灵光一闪 |
| 全量清单 | 未被遗忘的事件按 id 升序，每行「#id 标题 — 绝对日期 — 两条带编号的片段印象」 |
| AI 一段 | 全量清单判定：相关事件（≤6）、档位、expand 请求 |
| AI 二段 | 对 expand 的事件展开片段细节，最终判定档位 |
| 动作 | 选中 → 注入（指认段 summary / 同事件其余 gist / related 一行）＋ 擦亮；全程落库记录 |
| 兜底 | 无 Key / 调用失败 / 非法输出 → 现有本地检索（IDF 加权 / 相对截断 / Top3）原样接管 |

**旧逻辑的定位**：不参与主路径决策，只剩兜底与灵光一闪两处。它分不清「字面弱但语义对」和「字面强但语义错」，而这两类恰好是本次改造的对象（见第九节）。

## 三、全量清单

- 范围：`memory_events` 全库，排除 `upcoming`、默认事件，以及**实时权重 < 15 的事件**（已经淡到会被遗忘的那些）；
  - 权重在构建清单时用 `decay.ts` 的 `calculateWeights` **现算**，不建每日定时任务（手机端后台定时不可靠，项目时序约定本来就只认三个检查点）。权重只会随衰减单调下降、被擦亮时跳回 100，所以某个事件「跌破 15」全天最多发生一次，不会因此每轮打爆缓存；
  - **兜底路径共用同一过滤**：开关关掉或调用失败走本地检索时，候选池同样排除 <15，否则一降级冷记忆就全回来了；
  - **被排除不等于被删除**：灵光一闪的冷池本来就抽 `live_weight < 40`，所以这些事仍可能「突然想起」，一旦命中就擦亮回 100、重新进清单——遗忘是降级不是死刑，闭环成立；
- 排序：**id 升序**（缓存命中的关键——按其他列排会每轮变序打爆缓存；新事件 id 更大、天然追加在尾部，老前缀不变）；
- 每行格式：`#37 那次面馆探店 — 11月2日 — [f91] 加班后去吃了牛肉面 — [f88] 第一次去排了半小时队`
  - 标题之后带**该事件最近 1 条 + 最早 1 条片段的一句印象，并标出片段编号**——编号是指认细节的唯一依据：AI 看不到的东西没法指认。
  - 为什么只摆 2 条：1000 条库 × 全部片段会到几千行，注意力被稀释、缓存也贵；缺的部分由第二段在「拿不准」时补看。
  - 为什么是「最近 + 最早」而不是「和输入最像的」：后者又回到字面匹配，而「还开着吗」对「店关门了」零重合——正是要交给 AI 的那类。
- 占位符渲染（喂 AI 前必须做，判定调用是无上下文新会话）：
  - `[time]` → **绝对日期**（不用「3天前」——相对时间每天变，会把缓存打爆）；gist 没写 `[time]` 的由代码按事件时间补日期前缀；
  - `[user]` → 固定写「用户」、`[ai]` → 固定写「你」，**不渲染成真实昵称**：昵称可在设置页改，一改整份清单全变、缓存全废；且真名对判定没有信息增量，反而每条重复出现、稀释区分度。
- 体积参考：约 55 词元/条；200 条库 ≈ 11k 词元，1000 条 ≈ 55k 词元（千条库时清单该改成分层，见第九节）。

## 四、判定调用

### 时机

用户消息分词后有实词、且未被跳过闸门拦下即调用；`retrieve` 由同步改异步，聊天主流程 await。await 放在 `setLoading(true)` 之后即可——界面沿用现有「正在输入中」的打字动画，不必新增等待态，也不会出现判定期间重复发送。

### 跳过闸门（不调用 AI）

省的是**主链路延迟**（每轮 0.3~1s），不是钱。宁可漏省不可误杀：命中任一即当轮零事件、不调 AI；灵光一闪照旧（独立通道）。

判定前统一归一化：去空白、标点、emoji；折叠重复单字（嗯嗯→嗯）。

**覆盖检查（整句无信息才算跳过）**：表就是 `tokenize.ts` 的 `STOP_WORDS`——**一张表两用**（检索时当停用词、这里当覆盖词），口径统一才不会出现「检索认为有意义、闸门认为没意义」。从首字往后**最长匹配**，每个片段都必须被表吃掉；遇到吃不掉的片段立即判为「有实词」，转 AI。整句吃完 → 跳过。
   - 表的内容：**语法成分**（的/了/吗/呢/就/还/是/我/你/这/那…，含单字条目）、**寒暄答对**（早/早上好/晚安/在吗/在干嘛/吃了没/谢谢/对不起/好的/收到/嗯/哦）、**时间词**（今天/明天/昨天/现在/早上/中午/晚上/周/礼拜/星期）、**疑问与天气名词**（几号/几点/什么时候/多少/天气/下雨/气温）、**占位符残片**（user/ai/time/now）。长词优先、组合覆盖，不必逐句枚举。
   - 效果：`早上好`、`早上好啊你`、`今天几号`、`现在几点`、`今天天气怎么样`、`你早`、`吃了没`、`嗯嗯好的` 全部吃完 → 跳过；`今天几号考试来着`（考试）、`我今天好累`（累）、`好的妈妈`（妈妈）、`早上好我今天头疼`（头疼）吃到一半断掉 → 转 AI。
   - **表里绝不收情感词、身体状态、具名事物、动作**（累/工作/吃饭/开心/难过/头疼/猫…）：它们是想起往事的那根线，进了表「今天工作好累」就被当闲聊跳过。泛化情感词在检索侧同样不该停——写入侧要求标签带情绪词，它们能当单字/标签线索，去噪交给 IDF 权重。每加一个词都要问「这句话会不会指向某段回忆」，加错只有坏处：多调一次 AI 只是浪费，少想一件事是永久缺一根记忆。
闸门只有这一道：覆盖检查不改变「注入了什么」，只是省延迟，所以不再叠第二、第三道本地判定。「学到的白名单」与「同句 10 分钟内复用」都已去掉——它们省下的上限是 0.5 秒，换来的是要人维护的表和一个启用后再不可证伪的通道。

### 模型

走后台模型路由（便宜快速模型），JSON mode，temperature 尽量低。

### 请求结构（前缀缓存的关键顺序）

1. `[system]` 判定说明——固定不变；
2. `[user]` 全量清单——只随事件增删改、或有事件跌破权重门槛而变化；
3. `[user]` 今天日期 + 用户这句话——每轮全价，变化内容只放这里。

### 第一段输出

```json
{"hits":[{"id":88,"level":"core","frag":91}],"expand":[37,12]}
```

- `hits` ≤6：`level` 只能 core（明确谈论这件事本身）或 related（提到相关人/物/地点但话题不是它）；拿不准宁可漏判；
- **相关性是提示词里的硬要求**，不靠程序截断数量：不要放入只是字面沾边、说不太准的内容——一条错的往事会被顺着接话，比少想一件事破坏性大得多；
- `frag`：用户这句话真正指向的片段编号，**只能从该事件在清单里展示的两条里选**；指认不到就省略（渲染走「最近一条详细 + 其余一行」）。指认错了只影响详略、不影响注入哪件事，故不加重试；
- `expand`：事件级拿不准才请求，≤5 条，超限程序截断。
- **缺省与越界**（程序侧兜底，不指望模型守规矩）：`level` 缺失或非这两值 → 按 related（少给细节，宁缺勿滥）；`hits` 超 6 条 → 按 core 优先、其次原文顺序截断到 6；同一 id 重复 → 取第一条。

### 第二段（仅 expand 非空时）

- **职责**：给事件级拿不准的事件补看片段，再定档。看过的片段也允许被指认——模型指到第 3 条时不该丢掉，否则会退化成「讲最近那次」，细节给错。
- 请求 = 同样的说明 + 同样的清单（前缀缓存命中）+ 展开块 + 日期与用户话；
- 展开块：每个事件取**最近 ≤8 条片段**，每条带片段编号 + 一句话印象（占位符同规则渲染）；
- 输出：只对展开的事件给最终 `hits`、档位与 `frag`（frag 可从展开的片段里选）；
- 两段结果合并；第二段失败 → 用第一段结果。

### 校验与失败语义

- id 与 frag 都必须存在于库、且 frag 必须属于该事件（编造即丢弃，不影响该事件其余部分）；expand 编号非法丢弃。
- 解析容错：JSON mode 也可能带代码块包裹或前后废话，取第一个 `{...}` 再解析。
- **解析失败 / 请求失败 ≠ 零命中**：一律走兜底并把 `fallback` 置 1，绝不能当成「这轮没什么可想的」——否则会静默丢召回，还会连带丢掉擦亮。
- 不重试：失败就兜底，等下次；重试会把最坏情况从 1s 拖到 2~3s，收益不值。

## 五、注入与擦亮

- 注入：AI 选中的事件进记忆区（上限 6），**详略跟档位走**：

| 情况 | 注入内容 |
| --- | --- |
| core + 指认了 `frag` | **指认那条给完整 `summary`**，同事件其余给一行 `gist`（合计 ≤4 条） |
| core + 没指认 | 最近一条给 `summary`，其余一行 `gist`（不指认就讲最近那次） |
| related | 只一行：事件标题 + 一句 `gist` |

- **年龄曲线与 `detail_visible_weight` 在主路径不再参与详略判定**，只在兜底路径生效；设置页「记忆流转阈值」补一句说明（AI 判定开启时仅影响兜底）。
- **`cuedFragmentIds` 退出主路径**：详略由「档位 + AI 指认的片段」决定，本地词重合规则只在兜底路径保留。这也比原方案省：一个 core 事件从「4 段 summary」降到「1 段 + 3 行」。
- 擦亮（二值，无中间档）：AI 判相关（core/related）→ `active_weight=100`、`last_accessed=now`；未选中 → 不擦不注入。衰减照旧现场计算，不变。
- 灵光一闪命中 → 也擦亮（自然退出冷池几天，避免连抽同一条）。
- **衰减在主路径只剩三处作用**：清单的权重 <15 过滤、灵光一闪的冷池筛选（`live_weight < 40`）、兜底排序；注入与否与详略都不再读权重。

## 六、学习回路（不做）

第一段不再输出 `cue`，也就不存在把用户说法回写 `keywords` 的通路。理由：主路径（AI 判定）不读 keywords，这条回路只服务降级路径，却要引入写入口、查重与上限替换规则，还会把未经验证的说法混进标签体系。要提升兜底质量，拿标注集调 IDF 与截断线比在线学习划算。

## 七、判定记录（新表 `retrieval_logs`）

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `id` | PK | 自增 |
| `created_at` | TEXT | 调用时刻 |
| `user_text` | TEXT | 用户话语原文 |
| `stage1_output` | TEXT | 第一段完整 JSON |
| `stage2_output` | TEXT | 第二段完整 JSON，未触发为 NULL |
| `final_injected` | TEXT | 最终注入的事件编号 JSON |
| `fallback` | INTEGER | 1=本地兜底接管 |
| `event_count` | INTEGER | 清单事件条数 |
| `expand_used` | INTEGER | 是否触发第二段 |
| `latency_ms` | INTEGER | 总耗时 |

- 写入点：判定调用返回处，一处写入，不碰主流程；
- 被覆盖检查拦下的轮次不写日志（没有判定结果）；
- 刻意不存全量清单快照：事件自带时间戳，按「记录时刻」可近似还原当时清单；
- 保留策略：上限 5000 条，滚动清理；
- 用途：复盘 AI 判定、人工筛选反哺 `tests/cases/` 标注集、统计判定轮次占比与延迟、未来换模型/微调的语料。

## 八、兜底与开关

- 无 Key / 调用失败 / 输出非法 → **现有本地检索（IDF 加权 / 相对截断 REL_CUT / Top3）不删，降级为兜底**；与改造前唯一的差别是候选池同样排除权重 <15 的事件（口径与主路径一致）；
- **清单为空时不调用**（新装、清空数据后还没攒下记忆）：当轮零事件，不写日志、不计失败、也不跑兜底（本地池同样是空的）——否则会白花一次请求，还可能因为空消息报错被记成「判定失败」，误报成 Key 问题；
- 设置页新增「AI 检索判定」开关，默认开，关闭即回到本地检索路径（即当前实现，已不含分档门槛）；
- 失败原因写调试日志（检索条目），不弹窗——兜底路径聊天可用、记忆写入由下次调用恢复。
- **但连续失败要在设置页可见**：只写日志的话，Key 过期这类持续性故障会让体验静默退回老检索，没有出口。照巩固流的做法，连续失败 ≥3 次就在「AI 检索判定」下方标一行红字（仍不弹窗）。

## 九、明确不做

- **本地关键词强命中直接取记忆（绕过 AI 判定）**：旧方案的误报是「字面强、语义错」（否定句、同人不同事、硬干扰），收紧门槛只能削掉弱噪声，削掉的却是本次要捞回的召回；把已知会错的结果放进最快路径，还留不下判定记录，等于用不可复盘的方式牺牲质量；
- **判定合并进前台生成调用**（真能省掉这次往返）：擦亮要从前台回复里回收、每轮 6 条记忆摊在生成模型眼前容易「表演回忆」、判定无法单独复盘；
- 负样本存储（哪句话不该想起哪件事）；
- 历史判错案例喂给 AI（请求变长、缓存难命中）；
- 自动升降记忆优先级；
- 分档擦亮中间档（只做擦/不擦二值）；
- 主路径内的年龄插值（详略只看档位与指认结果，不再按权重分详细/简略档）；
- 跳过闸门的模糊/包含匹配，以及「学到的白名单」这类需要人维护、且启用后再不可证伪的本地判定；
- 整包导入公开中文停用词表：并集 2312 条、1090 条候选，多是书面语连词与四字成语（川流不息、反过来说），口语里几乎不出现，整包进仓库只是加一堆没人能逐条确认的词。其中 83 条经实测已并入（含「有点」——它本身不指向往事，先前看着像在承载召回，实为「关键词 ≤2 要求全中」这条门槛把整句否掉，门槛已改为命中 1 个即入候选）；公开表文件本身不进仓库；
- 向量嵌入（千条库量级后再评估）；
- 第二批：细节层「上次被想起时间」字段（常被提起的细节保持清晰，需动表结构）、千条库后的清单分层、按延迟数据决定是否扩大闸门覆盖。

## 十、成本与延迟预期

| 项 | 数字 |
| --- | --- |
| 清单缓存命中价 | 200 条库 ≈ 0.24 分/轮，500 条 ≈ 0.5 分/轮，1000 条 ≈ 1.1 分/轮（每行含 2 条片段编号） |
| 缓存失效重付 | ≈ 清单大小全价：事件增删改（巩固新增是尾部追加，不失效）或有事件跌破权重门槛时发生，后者每个事件一生只一次 |
| 第二段展开 | ≈ 2 厘/次，低频（只在事件级拿不准时） |
| 每天 100 轮（500 条库） | 约 5 毛/天（全部调用时的上限） |
| 实际调用轮次 | 只有闸门与「权重 <15 不进清单」在省：前者看说话习惯（寒暄多的用户可能省掉小半），后者让清单随遗忘变短，长期反而比全库便宜 |
| 遗忘过滤的收益 | 清单随遗忘自然变短，长期比全库便宜；被过滤的条目不再进 prompt |
| 记忆区 | core 指认到片段：1 段 summary + ≤3 行 gist ≈ 220 字；未指认：最近一段 summary + 3 行；related 一行 ≈ 40 字 |
| 延迟 | 有实词的轮次 +0.3~1s（随库增长）；触发二段再 +1~2s（低频）；被闸门拦下的轮次零延迟 |

## 十一、实施清单

## 十二、验证

- 离线：`npm test` 继续覆盖本地兜底路径（IDF 加权 / 相对截断 / Top3 仍在兜底生效）；改用例只动 `tests/cases/`；
- 详略：core 指认到 frag → 该条 summary + 其余 gist 一行；core 未指认 → 最近一条 summary + 其余一行；related 只有一行 gist；主路径无本地 cued 参与；
- 指认容错：frag 不存在或不属于该事件 → 丢弃该字段，按「未指认」渲染，不影响事件入选；
- 闸门：`早上好`／`早上好啊你`／`今天几号`／`现在几点`／`今天天气怎么样`／`你早`／`吃了没`／`嗯嗯好的` 零调用；`今天几号考试来着`／`我今天好累`／`今天工作好累`／`累死了`／`好的妈妈`／`早上好我今天头疼` 不跳过；
- 遗忘过滤：权重 <15 的事件不出现在清单，兜底路径同样排除；把某条调到 <15 后它仍可能被灵光一闪抽到，命中后擦亮回 100 并重新进清单；
- **AI 路径的离线回归**：`npm test` 只覆盖本地检索，改造后 AI 判定没有任何自动化回归。上线前把 78 例输入跑一遍真模型、人工核对结果、存成 fixture（一次性几分钱），之后调提示词或换模型先跑 fixture 看翻转——否则每次改提示词都只能上线赌；
- 上线：以 `retrieval_logs` 为准复盘——首周重点核对近邻混淆、否定句、纯情绪联想三类；统计判定轮次占比与延迟是否在预期内；
- 常规：tsc / lint 通过，`AGENTS.md` 无过时表述残留。

## 十三、风险与待决

- **隐私暴露面（已决定：接受）**：改造前外发的是「当前这句话 + 少数命中片段的摘要」；改造后每轮把**全部记忆的标题与一句印象**发给第三方接口，等于持续上传一份「用户记忆目录」。已确认按「判定质量优先」接受，代价要在设置页「AI 检索判定」下方写一句实话，别让用户以为记忆只在端上。
- **相关性只靠提示词约束，不做程序硬截断**：`hits ≤6` 只是格式要求，权重放在「不确定就别放」这条指令上。代价是无法在代码层保证上限，注入体积可能有波动；若上线后发现确有超量（连着 6 条 core），再考虑补硬限。
- **遗忘门槛（权重 <15）的边界**：被排除的事件只能靠灵光一闪回来，而灵光一闪是概率触发、且一次只抽一条。这意味着长期不提的事会真的沉底——这是产品想要的效果（会忘），但要清楚它是**单向降级**，用户主动问「还记得吗」时这类事大概率想不起来。门槛若引起体感落差，先降到 10 再观察。
- **缓存失效不是「每天一次」，是「每次记忆变更 + 每次有事件跌破权重门槛」**：巩固新增事件是尾部追加（不失效），但事件合并、标题编辑、upcoming 转常态、condition 关闭、权重跌破 15 都会改中间行。量级仍是几分钱，别按「日更」估。
- **判定期间巩固流并发写库**：本轮清单是快照，新写入的事件下一轮才可见，属预期行为，不是 bug。
- **注入总量**：AI ≤6 + 灵光一闪 1，最多 7 段记忆。
- **expand 与 hits 的 id 重叠**：以第二段结果为准，同一事件不重复注入。
- **千条库边界**：清单 55k 词元、约 1.1 分/轮、首字延迟可能接近 1.5s。到此量级必须改分层清单（第二批），不能硬扛。

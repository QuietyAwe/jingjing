评估边界

  • 分词（tokenize.ts）、屏蔽词（isBlockedGram）、门槛与打分（minHitScore / rankByOverlap）均取自真实源码并实际执行；SQL 粗召回用等价的字符串包含模拟。
  • 不含权重衰减、灵光一闪概率通道、Prompt 拼装；别名用事件自带的 alias 字段模拟（真实库是 memory_event_aliases 表），每条事件只有 1 条 gist + 1 条 summary，真实库片段更多，召回可能略高于本评估。
  • 理想命中按「真实陪伴场景下什么算恰当」人工标注，情绪类用例带有语义期待，纯字符串检索天然难以满足——这正是评估要暴露的。
  • 复跑：node tests/retrieval.eval.mjs，会重新生成本报告。

结论

以下数值取自本次运行。 1. 从「不敢接」到「该接的接住」：逐例全对 31/48 → 41/48，Recall 48.6% → 89.2%；代价是精确率 100.0% → 91.7%——多认回来的典型是「加班」顺带想起面馆（那件事本来就是加班后去吃面），算误伤，不算硬错。 2. 关键不在门槛，在「拿什么去比对」：只把门槛放宽到「长句命中 1 个词」（全字段、仍两段式）停在 38/48、副作用 3 例；把比对文本换成「一句话印象 + 写入时抽的标签」才到 41/48、副作用 1 例。summary 是完整叙述，「有点 / 觉得 / 一个人」这类虚词一撞就中。 3. 两条召回通道必须合并：上一版「标题命中就停」，于是「最近压力大，团子还生病了，都没好好吃饭」只想得起团子；合并后加班、团子、发烧三件都能想起来。分组变化——变差：I 边界 3/4 → 2/4；变好：C 换说法 3/7 → 7/7、D 情绪 1/5 → 3/5、F 身份名 1/3 → 2/3、G 长句 2/4 → 4/4、H 时间 1/3 → 3/3。 4. 剩下 7 条是机制与人的差距清单：单字「猫」在分词层被丢掉；纯情绪的「今天好累」没有任何字面线索；「加班」这类通用词会顺带擦到面馆；否定句「不是吃面，是火锅」挡不住；「有点想家」库里没写「想家」这个标签；一次说四件事时注入上限只给三条。 5. 情绪倾诉组 1/5 → 3/5：纯字符串检索无法从「累」联想到「加班」，属架构层面的差距，不是调参能补的。
